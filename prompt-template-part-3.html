Part 3 • Transform

Transforming data with prompts

In Part 1 you learned the template. In Part 2 you saw an end goal turned into a filled-in template. In Part 3 the job is a change of form: the same information, in a new type that a person, a program, or a platform can use.

Start here

What a transformation prompt is

A transformation takes source data in one form and returns it in another form, without inventing new facts. You name three things every time: the source, the target format, and what must stay true in between.

Vague“Make this nicer.”
No target format named, so the AI guesses the shape, and may rewrite, drop, or add facts while it guesses.
Clear transformation“Convert these notes into GitHub flavored Markdown. Keep every fact and number exactly as written. Use headings and a table. Add nothing.”
Source, target, and the fidelity rule are all named. You can check the result line by line.

The template, extended for transformations

CONTEXT: [What the source is, where it came from, and what it is for]
ROLE: Act as [type of expert or helper]
GOAL: Transform [source] into [target format], so [who or what will use it, and how]
CONSTRAINTS: [Exact target rules, what to keep word for word,
  what may change, and: add no facts that are not in the source]

The one rule that matters most: transforming changes the form, not the facts. If a value is not in the source, it does not go in the output. In your Constraints, say so plainly, and ask the AI to mark anything unclear as unclear in source instead of guessing.

Four questions before you send

  1. Source: What exactly am I giving it: pasted text, an uploaded file, a table, code?
  2. Target: What exact form must come back: Markdown, Python, JSON, CSV, an email, a table?
  3. Keep: What must not change: numbers, names, dates, wording, order, meaning?
  4. Check: How will I verify it: compare against the source, run the code, open the file in its real tool?

Use case map

Six transformations you will meet below

Rough text → MarkdownNotes and drafts become a production ready README or doc in GitHub flavored Markdown: headings, tables, task lists, code fences.
PDF paper → Python codeA method or algorithm described in a paper becomes working, tested Python that follows the paper, section by section.
Messy list → Table, CSV, or JSONUnstructured names, dates, and values become structured data a spreadsheet or program can read without retyping.
Transcript → Action itemsA meeting transcript becomes a short summary, decisions, and a task list with owners, plus a follow up email.
Code → Code in another languageWorking code becomes the same logic in a second language, with the differences explained, not silently changed.
Long text → Short formA long report or article becomes a summary, an FAQ, or slide headings, at a stated length, with no new claims.

Each example below shows a transformation as a diagram: the source, what must stay true, and the target it becomes, with a check at the end.

Visual 1 of 6 • Text to Markdown

Rough notes → production ready GitHub flavored Markdown

The job: Your project notes are a wall of plain text. GitHub needs structure before anyone can read or maintain them.

Sample source: paste this into the AI chat with your prompt

project setup. install: run pip install -r requirements.txt then copy .env.example to .env. to do: write tests is not done, deploy checklist is done. commands: start = python main.py, test = pytest. note the start command must run from the project folder.

Notes become a README

Source: rough notesPlain text setup notes for a small Python project, with commands, file names, and to do items.
→
What must stay trueEvery command, file name, and fact exactly as written. Add nothing that is not in the notes.
→
Target: README sectionGitHub flavored Markdown: ## headings, a table or list where it helps, a task list, fenced code blocks with the language named.

What to notice: Check it in a preview: does every command appear, unchanged, inside a code fence? Is the unfinished item shown as - [ ] and the finished one as - [x]?

Visual 2 of 6 • Paper to Code

PDF paper → Python code

The job: A paper describes a method in words, equations, and a results table. You want code that implements that method, so you can run it and test whether you understood it.

A paper becomes code you can run

Source: research paperA method in words, equations, and a results table.
→
What must stay trueOnly what the paper states. Where a value is not stated, write NOT STATED and ask, do not guess.
→
Target: Python codeStep 1: list the method steps and every parameter, each with its section. Step 2: implement them as one clear file. Step 3: add tests from the worked example numbers.

What to notice: Run the code and the tests. Do the test results match the numbers in the paper? If not, the transformation is not done yet, no matter how neat the code looks.

Visual 3 of 6 • Text to Structured Data

Messy list → table, CSV, or JSON

The job: Information trapped in sentences cannot be sorted, counted, or read by a program. Structured data can. The key move is naming the fields before you ask.

Sample source

Ana, paid 25 on Nov 2, by card. Ben paid 40, Nov 3, cash. Ana again, 10 dollars, Nov 5, card.

Sentences become a spreadsheet

Source: payment notesSentences like “Paid Maria $40 on March 3 by card.”
→
What must stay trueName the fields first: name, amount, date, method. Dates as YYYY-MM-DD, amounts as plain numbers, every value exactly as written.
→
Target: CSVOne row per payment, a header row, and a Missing list for blank fields. No rows and no totals you did not ask for.

What to notice: Count the rows: 3 payments means a header plus 3 rows. Open it in a spreadsheet and check the columns line up. For JSON instead of CSV, name the same fields as keys.

Visual 4 of 6 • Transcript to Tasks

Meeting transcript → summary, action items, and email

The job: A transcript is a record, not a plan. This transformation extracts only what was decided and who owes what, in a form people will actually read.

Sample source

Sam: The launch moves to Monday. Lee: I will finish the checklist by Friday. Sam: Good, I will email the client after that. Lee: And we still need a price check, nobody owns that yet.

A transcript becomes a plan

Source: transcriptA short planning meeting with Sam and Lee.
→
What must stay trueOnly tasks a person agreed to. The price check stays Unassigned, because nobody took it. No date said means NO DATE SAID. Invent no decisions.
→
Target: three thingsA summary of at most 3 lines, a task table with Task, Owner, Due, and a follow up email draft listing the same tasks.

What to notice: Read the output against the transcript. Is the price check wrongly given an owner? That is the most common error in this transformation.

Visual 5 of 6 • Code to Code

Python → JavaScript, and long text → short form

The job, first half: The same logic, in a language a different program can run. The meaning must survive even where the two languages work differently.

Sample source

def total(prices):
    return sum(p for p in prices if p > 0)

One language becomes another

Source: Python functiondef total(prices): return sum(p for p in prices if p > 0). Only values above zero count.
→
What must stay trueChange no logic. Same inputs, same output, same behavior.
→
Target: JavaScriptThe same function for a web page, plus a list of any behavior that differs between the languages, and one test input with the expected output, the same for both versions.

What to notice: Run both versions on the same test input, including an empty list and a list with zero and negative values. Same result both times is the proof.

Visual 6 of 6 • Your turn

Your own transformation

The job: Pick one real conversion from your own work. Common picks: an email thread into a task list, a recipe in a paragraph into a measured ingredient list, a web page into plain text notes, a spreadsheet column into a bulleted report.

Your transformation, as a routine

  1. Pick one real conversionAn email thread into a task list, a recipe paragraph into a measured ingredient list, a web page into plain text notes, a spreadsheet column into a bulleted report.
  2. Name the source and the targetWhat you have, and what you want it to become.
  3. Name what must stay trueThe facts, values, and details that must survive unchanged.
  4. Run it and check the outputAgainst the source, line by line. If a fact changed, the transformation failed.

Before you trust it

Fidelity checklist, for every transformation

  • Did I name the target format exactly: not “nicer”, but GitHub flavored Markdown, CSV with these fields, Python, JSON?
  • Did I say what must stay the same: numbers, names, dates, commands, wording, order?
  • Did I forbid invention in plain words: add no facts that are not in the source, mark unclear items instead of guessing?
  • Did I count in and count out: same number of rows, items, payments, or tasks as the source had?
  • Did I test it in its real tool: preview the Markdown, open the CSV, run the code and its tests?
  • If something is missing, I fix one line, usually the target rules in Constraints, and resend with the same source.

Remember: Source + target format + keep the facts = a transformation you can verify. A result you cannot check against the source is not finished.

Common failure modes

  • Invented detail: a date, owner, or step appears that was never in the source. Fix: the no invention line, plus a Missing or Unassigned list.
  • Silent loss: a row, caveat, or negative case quietly disappears. Fix: ask for a count, and compare it with the source.
  • Format that only looks right: a table that breaks on GitHub, CSV with commas inside values, code that was never run. Fix: test in the real tool before you use it.

Reference

Glossary: transformation terms

Short, plain definitions for the new terms used on this page. The Part 2 glossary covers Context, Role, Goal, and Constraints.

Transformation
Changing data from one form to another while keeping its facts the same.
Source
The original data you give the AI, in its starting form.
Target format
The exact form the output must take, such as Markdown, CSV, JSON, or Python.
Fidelity
How faithfully the output keeps the source facts, with nothing added, lost, or changed.
Markdown
A plain text way to mark headings, lists, and links with simple symbols, readable before it is rendered.
GitHub flavored Markdown (GFM)
The Markdown dialect GitHub renders, adding tables, task lists, and fenced code blocks with a language name.
CSV
Comma separated values: a plain text table, one row per line, that spreadsheets and programs can open.
JSON
A structured text format of named fields and values that programs read directly.
Field
One named piece of data in a record, such as name, amount, or date.
Extraction
Pulling only the wanted items, such as decisions and tasks, out of a larger text.
Transcript
A written record of spoken words, usually with the speaker named for each line.
Production ready
Finished enough to publish or use as is, after a check in its real tool, with no cleanup left for the reader.
